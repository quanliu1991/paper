# Taking Tokenization off the Host for Agentic LLM Serving

> 原文：[abs](https://arxiv.org/abs/2610.13325) · [PDF](https://arxiv.org/pdf/2610.13325)

> KTH 出品。prefix caching 把重复 prefill 省掉之后，全量 tokenization 反倒成了 TTFT 的最大单项和前端喂数瓶颈。GraphTok 把整条分词流水线做成一个可重放的 CUDA graph，bit 级复现 5 个主流 tokenizer 的输出，即插即用接入 vLLM 和 NVIDIA Dynamo。

## 背景与动机

先看 agent 负载的真实形态：TraceLab 统计约 4300 个真实 coding-agent 会话，中位每次模型调用带 **119K 个 cached-prefix token，但只新增 875 个 token**、输出 214 个；95.7% 的输入 token 都被 prefix cache 覆盖。上下文越来越长、每次只加一小截——这正是 prefix caching 的甜点区。

问题在两个绕不开的约束上：

1. **prefix cache 必须先拿到 token ID 才能查**。缓存按 token 块哈希索引，没分完词连「命中没命中」都无法判断。
2. **BPE（byte-pair encoding，从字节对逐步合并出 token 的分词算法，Llama/Qwen 等主流 tokenizer 的核心）不满足拼接安全**。在文本末尾追加内容可能改变结尾附近的切分结果，所以「只 tokenize 新 suffix 再拼上旧前缀」一般不成立——必须全量重切。

于是出现倒挂：cache miss 时 tokenization 只占 median TTFT 的 2%（Llama 3.1 8B，130k token）和 1%（Qwen3 32B，40.5k）；prefix cache 命中后飙升到 **67% 和 49%**，成了 TTFT 里最大的一块。外卖已经提前送到楼下（prefill 免了），下楼取餐的电梯（tokenization）反倒成了主要等待。

加 CPU worker 治标不治本：单请求延迟不变，还和 retrieval、orchestration、工具执行抢核——与 RAG 负载共置时 HF tokenizer 延迟涨 1.6–2.3×，只给 4 核时涨 27.4×。更致命的是规模问题：NVIDIA Dynamo 这种单前端要替整个 GPU fleet 分词，tokenizer 吞吐直接卡死前端能喂几张卡——121k token 流量下默认 tokenizer 只撑得起 2 张卡最忙小时的量。

## 方法

三个设计要求：D1 精确并行（不许改变 token 序列）、D2 图内容纳不规则负载、D3 全链路 GPU 化（不许留 host 瓶颈）。架构 = 家族专属前端 + 共享合并后端，整体捕成一个 CUDA graph（录制一次 kernel 序列、之后零开销重放）。

**1. 并行前端：把串行正则改写成边界谓词**

参考实现的 pre-tokenizer（BPE 前用正则把文本切成小段，合并不允许跨界）是逐位置推进的串行扫描。GraphTok 为每个 tokenizer 家族推导一个「位置 i 是否开启新 pre-token」的谓词，所有位置由 GPU 线程并行判断，前缀扫描补足单个线程缺的上下文。例：Llama 3 的数字规则 `\p{N}{1,3}`——某数字开启新 pre-token 当且仅当它是 run 起点、或 run 内偏移是 3 的倍数；segmented scan 算出偏移，`x12345` 切成 `123`/`45`，与从左到右的正则匹配逐位一致。GPT-2、Llama 3、Qwen 2.5、DeepSeek-V3（三段式规则）各出一个谓词；Gemma 3 走 SentencePiece 系（空格映射为 U+2581、Unicode 词表 + byte fallback），单独写前端。added tokens 走 device trie 优先直出 ID，剩下的区域才交给家族谓词。**这是精确性的代价：每支持一个新家族就要写一份谓词。**

**2. Warp 协作 BPE：跨 pre-token 天然并行，pre-token 内保序合并**

pre-token 之间本就独立，可全并行；pre-token 内部合并有序且数据依赖。GraphTok 的做法是一个 warp 包办一个 pre-token（≤64 符号）：每轮各 lane 查相邻 pair 的 merge rank，把 `(rank, position)` 打包进一个 word，用硬件 warp 规约 `__reduce_min_sync` 取全局最小——rank 唯一、同 rank 按位置左优先，恰好复现参考实现的合并顺序；合并后只更新受影响的邻居。65–512 符号的 pre-token 走 shared memory 里的锦标赛树（overflow path）。>512 符号的几乎必是单字符重复长串：按轮次一批应用同 rank 的合并（链上隔一取一），论文证明了这批合并与逐步串行执行完全等价。

**3. 塞进 CUDA graph：固定容量与活跃占用分离**

CUDA graph 的优势是免 launch、免 host 决策地重放，但 tokenization 的每个量（pre-token 数、合并数、输出长度）都依赖输入，常规做法（运行时查计数→分配→选 kernel）会把 host 拉回循环。GraphTok 的解法：buffer 和 launch grid 按**容量上限**预先分配好，设备端计数器/掩码记录每次重放的**实际占用**，kernel 自己跳过空行。host 稳态只做三件事：拷文本 + 小 header、launch 一次、从 mapped pinned memory 读输出计数。容量按 2 的幂分档（ladder，至多 8 个 context），首次遇到的档当场 capture 一次，之后全重用。三条合并路径在图内并行分支跑完，一个融合 kernel 拼装回文档顺序。

**4. CPU 回落与 dispatcher**

图重放有固定开销（小输入 floor 0.06–0.08 ms），短输入打不过 CPU。实测交叉点：16 KiB（ASCII 文本）/ 4 KiB（非 ASCII 字节超过 1/64），以下路由给内置的 gigatoken CPU 引擎。并发多时 dispatcher 把等待中的请求合成一次 graph replay，每请求 host CPU 省 2.9–8.2×。

**5. 集成与安全门**

vLLM 走 tokenizer-factory 钩子挂 adapter（310 行 Python + 100 行 C 扩展，不改一行 vLLM 源码）；Dynamo 加原生 Rust 后端，`DYN_TOKENIZER=graphtok` 一个环境变量切换。两处都保留参考 tokenizer 兜底；构造时 probe 对不上 token ID 就拒绝启动，而不是静默偏差；评测中每个 timed cell 都先验证 bit-exact 再计时。

## 实验

硬件：单张 H100 NVL + 96 线程 host（2× Xeon 6336Y）。

- **正确性（先于一切计时）**：5 vocab × 3 语料 × 10 长度 × batch 1–256，每个 cell 与参考 tokenizer（GPT-2 对 tiktoken，其余对 HF tokenizers）输出 bit 级一致。反面教材：GPUTOK 在 1M token 输入上输出 989,225 个 token——砍掉 pre-tokenizer，第 130 位就分叉；BlockBPE 同样删正则。
- **单请求延迟**：1M GPT-2 token 完整调用（含双向传输）**1.7–3.2 ms**。Llama 3 最大输入 1.70–1.76 ms：比最强 CPU 基线 gigatoken 快 **4.7–6.0×**，比 TokTier 的 GPU 路线快 7.9–12.9×，比 tiktoken 快 202–313×，比 HF tokenizers 快 865–1295×——后两者同样输入要 0.4–2.3 秒，相当于原来 1 秒的活现在 2 毫秒。
- **冷热差**：从未见过的文本上 GraphTok 只慢 1.03×（没有内容缓存可 miss），gigatoken 慢 4.5×（pre-token 缓存 miss）。warm 对比其实低估了 GraphTok 的优势。
- **批处理**（8k token 文档）：batch ≥8 全面领先，batch 32–64 对 gigatoken 峰值领先 2.9–3.8×；batch 256 达 41k–66k docs/s。
- **TokTier 自家基准**（SWE-smith 上下文）：比 gigatoken 快 2.6–3.9×、比 TokTier 快 2.0–18.1×；≥1M 字符起 P99 也全场最低（4.4M 字符处 14.2/14.4 ms，vs TokTier 27.6、gigatoken 51.0）。
- **vLLM 端到端**（99% 前缀复用，32k–128k prompt）：mean TTFT 提升 **2.06–2.43×**；stock tokenizer 占 TTFT 的 56–76%，GraphTok 只占 1.4–2.5%；262k token 处 median TTFT 110 ms vs stock 1077 ms。但注意：单请求无争用时快 CPU tokenizer 与 GraphTok 只差 3–18%——单请求场景收益有限，真正的分化在容量和 CPU 争用。
- **Dynamo fleet 容量**（2s P99 目标）：121k token 流量下默认 tokenizer 撑 18.5 req/s（= 2 张卡最忙小时的量，9.25 req/s/卡）、TokTier 111（12 卡）、gigatoken 296（32 卡）、GraphTok **518（56 卡）**。512k / 1M token：129.5（14 卡）/ 46.25（5 卡），为 gigatoken 的 1.75×/2.5×；拐点处 gigatoken 的 P99 比 GraphTok 高至 64×。单请求 tokenize 阶段从 235 ms 压到 1.2 ms。极限已不是 tokenizer：换成 hash stub（无词表无合并）后前端 444/111/37 req/s，与 GraphTok 只差一步——**下一个瓶颈是 Dynamo 自己的请求解析/模板渲染/块哈希**。
- **与 coding agent 共享宿主机**（128 个真实 SWE-smith agent 跑真实工具调用，host 95–98% 忙）：GraphTok 全分位最快（p50/p90/p99 = 29/54/93 ms，比 gigatoken 低 14–17%）。256 agent + 590k token 长上下文时默认 tokenizer 和 TokTier 只能接住 1–2% 的调用（CPU 被 agent 吃光），GraphTok 与 gigatoken 全部接住。**每调用 host CPU：130k token 处 GraphTok 0.19 ms vs gigatoken 1.68 ms（8.7×）**；每 1000 calls/s 的 130k 流量，gigatoken 要占 1.7–1.8 核、GraphTok 只要 0.2–0.4 核——省下的核正好还给 agent 的编译和测试。
- **与模型共卡**：在推理 GPU 上分词只占 1.3%（130k prompt @ 5.5 calls/s）到 6.7%（590k @ 10.8 calls/s）的 GPU 时间、3–5 GB 显存；vLLM 吞吐变化 ±1.1%（基线自身窗口波动就有 2.9%）。原理：峰值负载下 vLLM 也只占用 24% issue slots / 18% warp slots / 57% tensor / 20% DRAM 读带宽——decode 是访存密集型，正好把大片空闲算力让给分词这种轻 kernel（MPS 共调度，不分时）。
- **graph 重放的贡献**：128–2k token 省 21–23%，32k+ 省 12%。阶段画像：BPE 合并是最大阶段；被先行者以「太贵」为由砍掉的 pre-tokenization 其实不占大头。

## 复现要点

- **代码**：<https://github.com/Msiavashi/GraphTok>（开源；~11k 行 C++/CUDA，其中 kernel + graph capture ~4.8k 行）
- **依赖**：CUDA 12.6、driver 595.71.05、sm_80+（`__reduce_min_sync`）；CPU 回落内置 gigatoken（MIT，Rust 静态链接）
- **集成**：vLLM tokenizer-factory adapter；Dynamo `DYN_TOKENIZER=graphtok`（fleet 评测再加 `DYN_GRAPHTOK_DISPATCH=1`）
- **支持家族**：GPT-2 / Llama 3 / Qwen 2.5（Qwen 3 同配置）/ DeepSeek-V3 / Gemma 3；Gemma 暂无 batch 路径
- **负载**：BurstGPT 最忙小时拟合（9.25 req/s，Gamma 形状 1.2）、SWE-smith 轨迹、OpenAssistant 多语料
- **最小路径**：clone → build → Python 扩展对拍 HF tokenizers 输出（自带 correctness gate）→ 挂 vLLM adapter，跑长 prompt cache-hit 场景看 TTFT 分解
- **注意**：交叉点以下自动走 CPU 路由；论文全部实验单张 H100，无跨硬件 scaling 数据

## 启发与局限

- 「固定容量 + 设备端活跃计数」是把变长、不规则的工作塞进 CUDA graph 的通用手法，不止分词能用——任何想图化的 host 侧变长处理（chat 模板渲染、采样后处理）都可以抄。
- 「prefix caching 之后 host 固定开销逐个暴露」这条叙事线很完整：tokenization（本文）→ 请求解析/模板/块哈希（stub 实验证明的下一个瓶颈）→ 展望 device-resident token ID 直连 KV 路由（与 Blink 的 CPU-free 方向汇合）。缓存和更快的 prefill 每省一块 GPU 时间，剩下的 host 阶段就决定延迟，得逐个搬走或干掉。
- 精确性优先的工程伦理值得学：不支持的配置直接拒绝而非近似；每个 timed cell 先验证 bit-exact；probe 失败拒绝启动而非静默降级。GPU 重写最容易悄悄改变语义，这套 gate 是所有数字可信的前提。
- 局限：每个新 tokenizer 家族要手写前端谓词（作者明说是 exactness-first 的代价，通用性以 5 个已评测配置为界）；Dynamo 实验 GPU 是模拟的（测前端容量，非端到端 TTFT）；单请求 vLLM 场景对快 CPU tokenizer 优势只有 3–18%，真正的卖点在 fleet 容量与 host CPU 争用两类场景。

## 疑问清单

1. overflow 路径的批量合并只对「单字符重复长串」给了等价性证明；构造一个交替模式的超长 pre-token（如 `"ab"` 重复上万次）会退化到什么程度？论文只说非重复文本最多浪费一轮就转交锦标赛树。
2. dispatcher 把并发请求合成一次 replay，短请求队列在 60k req/s 处已见排队（p50 0.3–0.65 ms）；混合长短请求时，长请求会不会把短请求堵在同一 batch 里（head-of-line blocking），P99 怎么走？
3. token ID 已能留在设备上（handoff 6b），但 Dynamo 的块哈希和 KV 路由还在 host。把 prefix-cache 哈希也搬上 GPU、彻底消掉这次 host 往返，收益还剩多少？stub 实验的 518 vs 444 req/s（~15% 差距）大概是这个方向的上界？

## 新学到的术语

- **BPE (Byte-Pair Encoding)**（learning）：从字节对逐步合并出 token 的分词算法，GPT-2/Llama/Qwen 等主流 tokenizer 的核心；合并在 pre-token 内按 rank 有序进行
- **Pre-tokenization**（learning）：BPE 前用正则把文本切成 pre-token 小段、合并不许跨界的一步；删掉它会改变最终 token 序列（BlockBPE/GPUTOK 的病根）
- **gigatoken**（learning）：目前最强的 CPU BPE tokenizer 库（Rust，SIMD + pre-token 缓存），serving 论文常见最强 CPU 基线
