# DLoop: Looped Speculative Decoding

> NAVER AI Lab 等。解决 draft 模型变强之后，投机解码「起草一段就验证一段」的固定节奏造成浪费的问题。

## 背景与动机

投机解码像实习生起草、老板审批：实习生（draft model）一口气写出几个字，老板（target model）扫一眼全部通过或打回重来。论文观察到一件事：draft 模型越来越强，老板经常**全批**——实习生写的全对，可系统还是按老规矩「写一段、批一段」，老板每段都要起身看一遍，哪怕这段根本不用改。多余的审批（verification，即 target model 前向）就是纯浪费：本可以让学生继续写下去。

已有 adaptive draft length 方法的问题是它们只对自回归 draft 模型有效。而并行 draft 模型（EAGLE 一类，起草时要用 target 的 hidden states）想多写几段，会遇到一个死结：后续段需要「还没被验证过的 token」对应的 target hidden states——这个东西不存在，老板还没看，哪来的批注。

## 方法（据摘要）

三个动作：

1. **连续起草、合并验证**：draft 模型对自己的输出有信心就继续写下一段，把多段 draft token 攒起来，最后一次性交给 target 验证。核心交换：多花几次便宜的前向（draft），省掉昂贵的前向（target）。
2. **loop-aware training**：让 draft 模型在「继续写」的段里以**自己生成的 hidden states**（对应未验证 token）作为输入训练，适应这个训练时没见过的新输入分布——没有这一步，draft 在第二段起就不可靠了。
3. **通用叠加**：不绑定某一投机解码方法，EAGLE-3、DFlash、Domino、DSpark、multi-token prediction 模块都能直接套。

## 实验（据摘要）

- 叠加在 EAGLE-3 / DFlash / Domino / DSpark / MTP 上，wall-clock 加速再提 **5–41%**。
- 保持 lossless decoding（投机解码的数学无损性质不变——输出分布严格等于 target 单独解码）。
- 代价：额外的 draft 前向（用便宜的换贵的）。

## 启发与局限

- 「全批率上升 → 逐段验证成浪费」是对投机解码瓶颈转移的敏锐观察：系统瓶颈会随组件强弱变化移动位置，加速方法要跟着重设计节奏，这是和 TokenRouter 的 delayed-batching（批准入延迟随路由频率变化重新设计入批时机）同款的「先 profiling 找真瓶颈、再动调度」思路。
- loop-aware training 本质是分布对齐：推理时的新输入分布（自身 hidden states 替代 target hidden states）训练时不存在，用轻量微调补齐——这个「推理形态改变 → 训练跟着适配」的模式在 speculative decoding 里反复出现（EAGLE 的 draft 训练同源）。
- 局限（据摘要推断，待正文验证）：confidence 判据依赖 draft 模型自评，误判（自以为行结果大量被拒）时多段合并验证反而拉长单次验证失败的代价；摘要未给单方法增益与 batch/并发场景表现。

## 疑问清单

1. confidence 判据具体是什么（logits 熵？top-1 概率？校准分数？），阈值怎么定、是否随模型/任务重调？
2. 多段合并后单次验证失败的回滚粒度：拒绝时退回哪一段？失败的累积 draft 是否全部作废（若全废，失败代价随 loop 段数放大，最优段数如何推导——是否有类似 TokenRouter B* 的解析模型）？
3. 与 DSpark/Domino 等 parallel drafter 叠加时，「未验证 token 的自身 hidden states」替换 target hidden states 是否引入质量偏移（loop-aware training 消除了多少）？
