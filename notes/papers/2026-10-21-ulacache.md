# UlaCache：给 GPU+CPU 的 KV 存储统一门牌号，稀疏注意力按门牌取件

> 原文：[abs](https://arxiv.org/abs/2610.29820)

## 背景与动机

DeepSeek-V4.1-Flash、GLM-5、Qwen3.8-Flash-Next、Step 5 这些新一代模型都带 index-based 稀疏注意力——每步只挑历史 token 的一个子集来算注意力。读的 KV 少了，但**存的问题没解决**：没被选中的历史还得留着（下一步可能被选中），历史照样随上下文和并发数增长，GPU 显存还是不够。

现有的两条 CPU 扩展路线各有堵点：

1. **HiCache/LMCache（前缀复用）**：CPU 缓存可复用前缀，命中后装回引擎的 GPU 槽位。但**活动请求的历史仍占 GPU 槽**——CPU 加再多，decode 并发上限还是被 GPU KV 槽位卡死
2. **HiSparse（历史外移）**：完整历史放 CPU，每步把选中 KV 拉到 GPU 的**固定每请求配额 buffer**。并发能超 GPU 容量了，但 GPU buffer 里是 CPU 数据的副本，不增加独立容量——实测 53.3M 物理槽只装了 30.0M 份独立历史，GPU+CPU 的空间没有真正「合并」成一块用

还有 TP 下的暗坑：MLA 的 KV 是全头共享的压缩表示，head 切分不切它——8 卡 TP 时每卡存一份完整副本，**87.5% 的分配是重复存储**。

UlaCache 的问题定义：让 GPU 和 CPU 的 KV 存储真正池化，一份历史只存一处，decode 并发随总容量扩展。

## 方法

核心抽象：**统一逻辑地址空间**。引擎侧只拿逻辑地址（稳定的门牌号）分配和选址 KV，物理上落在哪块 GPU、哪个 CPU 槽由 UlaCache 的地址映射决定，数据搬家只改映射不改门牌。

![系统架构](../assets/2610.29820-fig-overview.svg)

- **DP 模式**：每 rank 独立地址空间覆盖自己的 GPU 池 + CPU 池
- **TP 模式**：P 个 rank 的池子聚成分布式地址空间，历史按 `t mod P` 切到不同 GPU——MLA 共享表示不再每卡一份，8 卡的聚合容量直接 ~8×；计算 rank 另有一个小的本地 GPU buffer 缓存已取过的选中 KV（buffer 命中就不跨卡取了，只传缺失条目）

**PB-LRU（并行桶式 LRU）**：所有请求共享 GPU 池后的替换策略。把槽位按「最近访问在哪一轮」分桶（bitmap 表示，一位一槽），访问时 GPU 线程并行更新 recency；淘汰时用层级摘要 bitmap 跳过空区、从冷桶往外挑，**当前桶受保护**（本步注意力正要用的数据不会被踢）。对比 naive 时间戳 LRU 的全池扫描，调度快 1.5-2.3×（高压时），命中率差异 <0.1pp。

**交换协议**：先传数据后改映射——CPU 数据升入 GPU 槽的同时，被替换的 GPU 数据滑入腾出的 CPU 槽（一对一对调，不用额外分配 CPU 空间）；全部传输完成后一次性提交地址映射更新，注意力等完成信号。

**层组复用**：共享稀疏选结果的层组只做一次地址查找/去重/槽分配，访问计划复用 + CUDA stream 预取与计算重叠。

## 实验

SGLang 集成，GLM-5.3（FP8 权重与 KV），8×H200（CPU 128GB/卡）与 8×B300（CPU 192GB/卡），Multi-LexSum 64K-128K 输入。基线：SGLang（纯 GPU）与 HiSparse（最新官方实现），开投机解码（MTP 2 步 draft）：

| 配置 | 峰值 decode 吞吐 vs HiSparse |
|---|---|
| H200 DP / TP | 1.16× / 1.70× |
| B300 DP / TP | 1.73× / 2.51× |

![吞吐对比](../assets/2610.29820-fig-throughput.svg)

- 不开投机时 B300 TP 峰值吞吐 = SGLang 的 3.51×——更多请求同时活着，批大了摊薄执行
- 低并发（BS1）时 UlaCache 慢于纯 GPU SGLang（查找/调度/TP 通信的小开销）、快于 HiSparse（共享池能装下全部活动 KV，不用从 CPU 拉）
- 容量图：TP 模式下 8 卡聚合 + CPU 扩展后，独立历史容量数倍于基线，admission（可同时 decode 的请求数）相应抬升

## 启发与局限

- 「统一逻辑地址」是操作系统虚拟内存的老思想搬到 KV 管理——对比 PagedAttention（GPU 内分页）、vAttention（虚拟地址连续）、Mooncake（跨节点共享），UlaCache 补的是「**活动请求历史跨 GPU+CPU 池化**」这一格
- MLA 的 TP 复制问题（87.5% 冗余）被 TP 分布式地址顺手解决，这对 GLM/DeepSeek 系 MLA 模型的 TP 部署是实打实的容量红利
- 稀疏注意力把「每步读多少 KV」降下来了，UlaCache 把「总共能存多少历史」提上去——两者组合才是长上下文高并发的完整解；这也解释了为什么新一代原生稀疏模型（V4.1-Flash 等）出来后这类系统工作会密集出现
- 局限：BS1 时比纯 GPU 慢（管理开销），说明该系统瞄准的是高并发批量场景而非交互单请求；论文未开源是硬伤；GLM-5.3 单模型验证，MLA 之外的 GQA 模型 TP 切分本来就不复制 KV，收益结构会不同
